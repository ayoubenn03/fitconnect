Ce qu'on a codé, et pourquoi

01

Le pattern "snapshot" dans Booking

Booking a un classId — mais aussi className, classDate, instructor et price dupliqués en dur. Ce n'est pas de la redondance par erreur : c'est volontaire. 

booking-service/.../model/Booking.java// classId pointe vers class-service, MAIS on duplique aussi :
private Long classId;
private String className;      // copié depuis class-service au moment de la réservation
private LocalDateTime classDate;
private String instructor;
private BigDecimal price;      // le prix PAYÉ, pas le prix actuel du cours

Question posée : 3 semaines après une réservation, l'instructeur du cours change dans class-service. Que doit afficher GET /api/bookings/{id} pour la réservation déjà créée ?

→ L'ancien instructeur. La valeur du snapshot ne change jamais rétroactivement — exactement comme une facture garde le prix du jour de l'achat même si le tarif change ensuite. C'est ce qui a été réellement réservé et payé. Si on rappelait class-service à chaque lecture pour "rester à jour", le snapshot ne serait qu'un cache inutile, et surtout GET /api/bookings/{id} deviendrait indisponible dès que class-service tombe — alors que la réservation, elle, doit rester consultable.
02

Verrouillage optimiste sur FitnessClass

Deux étudiants réservent en même temps la dernière place d'un cours (currentParticipants=9, maxParticipants=10). 

class-service/.../model/FitnessClass.java@Version
private Long version;   // Hibernate ajoute "AND version = ?" au WHERE de chaque UPDATE

public void reserveSpots(int spots) {
    if (this.currentParticipants + spots > this.maxParticipants) {
        throw new IllegalStateException("Plus de places disponibles");
    }
    this.currentParticipants += spots;
}
class-service/.../service/ClassService.java@Transactional  // ← c'est CETTE frontière qui déclenche la vérification de version,
                 //   pas une annotation sur l'entité (un POJO n'est pas un bean Spring)
public ClassResponse incrementParticipants(Long id, int spots) {
    FitnessClass c = getClassOrThrow(id);
    c.reserveSpots(spots);
    return ClassMapper.toResponse(classRepository.save(c));
}

Le 1ᵉʳ appel réussit et la version passe de 4 à 5. Le 2ᵉ appel, qui avait lu la version 4, tente un UPDATE ... WHERE id=? AND version=4 : 0 ligne affectée → ObjectOptimisticLockingFailureException → 409 renvoyé au client. Aucun verrou posé en base, juste une vérification a posteriori — donc pas de lecteurs bloqués.

03

Feign + Circuit Breaker : piège du "409 qui casse tout"

feign.circuitbreaker.enabled: true enveloppe automatiquement chaque appel de ClassClient, PaymentClient, NotificationClient dans un CircuitBreaker Resilience4j. Un cours complet renvoie un 409 (NoSpotsAvailableException côté class-service) — un événement normal, pas une panne.

Le piège : sans configuration, Resilience4j compte TOUTE exception (y compris un 409 métier) comme un échec. Un cours populaire qui refuse plein de réservations en 409 finirait par ouvrir le circuit — alors que class-service tourne parfaitement.

config-repo/booking-service.ymlresilience4j:
  circuitbreaker:
    configs:
      default:
        ignore-exceptions:               # ne comptent PAS comme un échec du circuit
          - feign.FeignException$NotFound
          - feign.FeignException$Conflict
          - feign.FeignException$BadRequest

Ces exceptions continuent de remonter normalement (booking-service les attrape toujours dans un try/catch pour les traduire en 400/409 côté client) — elles ne comptent simplement plus dans le taux d'échec qui déclenche l'ouverture du circuit. Seules les vraies pannes (timeout, connexion refusée, 5xx, circuit déjà ouvert) font basculer class-service en "indisponible".

04

Saga : orchestration + compensation dans createBooking

Une Saga = une suite d'étapes locales, chacune dans un service différent, sans transaction distribuée qui engloberait les 4 services. Si une étape échoue après qu'une étape précédente a réussi, on ne "rollback" pas au sens SQL — on appelle une action de compensation qui annule l'effet de l'étape précédente. 

booking-service/.../service/BookingService.java// Etape 1 : lire le cours (snapshot)
ClassDto fitnessClass = fetchClass(request.getClassId());

// Etape 2 : reserver les places. Si 409 ici -> rien n'existe encore -> rien a compenser (Cas 2 du sujet)
reserveSpots(request.getClassId(), request.getNumberOfSpots());

// Etape 3 : persister la reservation. Si CA echoue apres l'etape 2 reussie...
try {
    saved = persistNewBooking(request, fitnessClass);
} catch (RuntimeException ex) {
    safeReleaseSpots(request.getClassId(), request.getNumberOfSpots());  // ← COMPENSATION
    throw ex;
}

Deuxième compensation, symétrique, dans cancelBooking : une réservation PENDING_PAYMENT annulée n'a jamais été payée (rien à rembourser), mais elle avait déjà pris des places à l'étape 2 de sa création — decrementParticipants est donc appelé dans tous les cas (CONFIRMED et PENDING_PAYMENT), alors que le remboursement ne l'est que si le statut était CONFIRMED. Piège classique : oublier de libérer les places d'une réservation jamais payée.

05

Notifications : effet de bord "best effort"

notifyBestEffort(...) attrape toutes les exceptions et se contente de logger — contrairement à reserveSpots qui, lui, propage l'erreur.

→ Une réservation valide et payée-à-venir ne doit jamais échouer parce que l'envoi d'un email a raté. L'email est une conséquence de la réservation, pas une condition de sa validité — à l'inverse, "avoir une place" (reserveSpots) est une condition : sans elle, la réservation elle-même n'a pas de sens. Cette distinction (étape constitutive vs étape secondaire) est ce qui détermine, dans une Saga, ce qui doit bloquer/compenser et ce qui peut simplement être retenté ou loggé.
06

payment / notification : simuler sans mentir sur l'état

Les deux services "terminaux" de la Saga (rien ne les appelle après eux) partagent une règle : chaque tentative est enregistrée avec son vrai résultat, jamais seulement les succès. 

payment-service/.../service/PaymentService.javapayment.setStatus(request.getAmount().compareTo(rejectionThreshold) < 0
        ? PaymentStatus.SUCCESS
        : PaymentStatus.FAILED);
// -> sauvegarde dans TOUS les cas : un paiement FAILED est une donnee utile (historique/debug),
//    pas une erreur a ne pas persister. refund() verifie ensuite explicitement status == SUCCESS.

Coté notification-service, même logique : l'envoi simulé peut échouer (~10%, aléatoire), le statut réel (SENT/FAILED) est stocké, et GET /api/notifications/pending renvoie les FAILED — exactement ce que PATCH /{id}/retry doit pouvoir retenter. Le seuil de rejet du paiement (100€) est dans config-repo/payment-service.yml, pas codé en dur : ajustable sans recompiler, comme tout le reste de la config métier.

07

Scheduler : séparer "quand" et "quoi"

BookingScheduler ne contient que deux méthodes @Scheduled qui délèguent immédiatement à BookingService. Toute la logique (requêtes, libération de places, notifications) reste dans le service.

booking-service/.../scheduler/BookingScheduler.java@Scheduled(cron = "${booking.scheduler.expire-pending-payments-cron:0 */5 * * * *}")
public void expirePendingPayments() {
    bookingService.expirePendingPayments();   // toute la logique est testable SANS attendre un cron
}

Pourquoi une fenêtre [maintenant+24h, maintenant+25h) pour les rappels, plutôt que "classDate - 24h <= maintenant" ? Le job tourne une fois par heure : avec une fenêtre glissante d'exactement 1h de large, chaque réservation confirmée ne peut traverser cette fenêtre qu'une seule fois entre deux exécutions — un seul rappel envoyé, jamais de doublon (si la condition restait vraie sur plusieurs exécutions) ni d'oubli (si le job ratait le instant précis).

08

Tester une Saga sans jamais démarrer les 4 services

BookingServiceTest ne lance ni class-service, ni payment-service, ni notification-service — les 3 @FeignClient sont des @Mock Mockito au même titre que le repository. On teste uniquement l'orchestration (l'ordre des appels, les compensations), jamais le réseau. 

booking-service/.../service/BookingServiceTest.java@Mock private ClassClient classClient;
@Mock private PaymentClient paymentClient;
@Mock private NotificationClient notificationClient;
@InjectMocks private BookingService bookingService;

when(classClient.incrementParticipants(101L, 2)).thenThrow(conflictException());
// ...
assertThatThrownBy(() -> bookingService.createBooking(request))
        .isInstanceOf(NoSpotsAvailableException.class);
verify(bookingRepository, never()).save(any());  // Cas 2 : rien n'a été persisté

Problème concret : FeignException.Conflict n'a pas de constructeur simple — il exige un feign.Request réel (méthode, URL, headers…), car en production c'est Feign lui-même qui le construit à partir d'une vraie réponse HTTP. Pour simuler un 409 en test, il faut donc fabriquer ce contexte à la main : 

BookingServiceTest.java — fabriquer un 409 sans réseauRequest request = Request.create(Request.HttpMethod.PATCH, "/api/classes/101/increment",
        Map.of(), null, StandardCharsets.UTF_8, new RequestTemplate());
return new FeignException.Conflict("conflict", request, null, null);

Au niveau du contrôleur, BookingControllerIntegrationTest change d'échelle : Spring démarre pour de vrai (@SpringBootTest), la requête traverse contrôleur → service → H2 réelle, mais les 3 clients Feign restent remplacés via @MockBean — on garde un test d'intégration de booking-service seul, jamais un vrai appel réseau vers un autre service.

→ Autre cas à part : ClassOptimisticLockingIT (carte 02) est le SEUL test qui a besoin d'un vrai ObjectOptimisticLockingFailureException — donc aucun mock ici, et surtout pas de @Transactional sur la méthode de test elle-même : avec une transaction englobante, Hibernate garderait un seul et même objet en cache de premier niveau pour les deux lectures, et le conflit de version ne pourrait jamais se produire. Il faut deux lectures vraiment indépendantes pour obtenir deux copies désynchronisées de l'entité, exactement comme deux requêtes HTTP concurrentes en production.
09

Piège Docker : un reactor Maven multi-module a besoin de TOUS ses poms

Chaque Dockerfile construit avec un contexte = la racine du repo, puis ne COPY que quelques fichiers avant de lancer mvn -pl <module> -am package — pour profiter du cache de couches Docker (les pom.xml changent rarement, le src/ change tout le temps). 

class-service/DockerfileCOPY pom.xml .
COPY eureka-server/pom.xml eureka-server/pom.xml
(... les 9 pom.xml de TOUS les modules, meme ceux qu'on ne construit pas ici ...)
COPY class-service/src class-service/src
RUN mvn -q -pl class-service -am package -DskipTests

Le piège : pom.xml (racine) déclare 9 modules dans <modules>. Pour construire le reactor Maven — même avec -pl class-service, qui ne compile qu'un seul module — Maven doit d'abord lire le pom.xml de chacun des 9 modules déclarés. Un seul manquant dans l'image (ex: on avait oublié de copier booking-service/pom.xml dans le Dockerfile de class-service) et le build entier échoue avec "Child module ... does not exist" — alors que class-service, lui, n'a strictement rien à voir avec booking-service.

→ Ajouter un module au reactor (les 4 nouveaux services) impose de mettre à jour le COPY des pom.xml dans tous les Dockerfiles existants, pas seulement d'en écrire 4 nouveaux — eureka-server/Dockerfile, config-server/Dockerfile, api-gateway/Dockerfile, product-service/Dockerfile et order-service/Dockerfile ont tous dû être corrigés pour cette brique, sinon docker compose up --build aurait cassé des services qui n'avaient pourtant pas changé une seule ligne.
